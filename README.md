# Longitudinal Patient Knowledge Graph + GraphRAG

This project explores how synthetic electronic health record data can be transformed into a trustworthy longitudinal patient knowledge graph and, eventually, a grounded GraphRAG application.

## Use case

Healthcare information is commonly distributed across encounters, diagnoses, medications, procedures, observations, and care plans. The goal of this project is to connect those records into an explainable patient journey while preserving clinical context, time, and source provenance.

The completed system should support questions such as:

- What happened throughout a patient's healthcare journey?
- What occurred around a particular diagnosis or intervention?
- How did treatment change over time?
- Which clinical, social, or financial factors appear in the patient's history?
- What source evidence supports an answer?

The project uses publicly available synthetic EHR data generated by [Synthea](https://synthea.mitre.org/). It is intended as a data-engineering and knowledge-graph learning project, not a clinical decision-support system.

## Planned approach

Development will proceed incrementally:

1. Profile the raw Synthea CSV datasets and understand their grain, identifiers, relationships, temporal semantics, and quality issues.
2. Build reproducible staging and normalization pipelines while keeping the source files immutable.
3. Validate data quality and referential integrity before creating graph relationships.
4. Design a longitudinal patient knowledge graph that distinguishes patient-specific events from canonical medical concepts.
5. Preserve timestamps and provenance, and keep derived assessments distinguishable from source facts.
6. Load the graph into Neo4j using stable identifiers and idempotent ingestion patterns.
7. Prove useful graph retrieval with explicit queries before introducing an LLM.
8. Add GraphRAG that retrieves a focused evidence subgraph and produces grounded, traceable answers.

Potential future hybrid retrieval may combine graph traversal for relationship-heavy questions, vector retrieval for semantic matching, and SQL for analytical queries.

## Initial data scope

The first iteration will use one patient with a multi-year history drawn from:

- `patients.csv`
- `encounters.csv`
- `conditions.csv`
- `medications.csv`
- `procedures.csv`
- `observations.csv`
- `careplans.csv`

The pipeline will be designed so the cohort can later expand without rewriting downstream processing.

## Guiding principles

- Keep raw source data immutable.
- Validate relationships before turning them into graph edges.
- Preserve original identifiers and source information.
- Treat time and provenance as first-class data.
- Separate source facts, normalized facts, and derived knowledge.
- Avoid unsupported clinical or causal conclusions.
- Keep each stage small, testable, reproducible, and explainable.

## Repository layout

```text
data/
  raw/                  # Immutable source files (not committed)
  staged/               # Cohort-scoped extracts
  normalized/           # Data conforming to the internal contract
  graph_ready/
    nodes/              # Graph node exports
    relationships/      # Graph relationship exports
src/
  profile/              # Source profiling
  stage/                # Cohort staging
  normalize/            # Normalization
  validate/             # Data-quality validation
  graph_transform/      # Graph-ready transformations
reports/
  data_quality/         # Generated quality reports
queries/                # Graph and retrieval queries
tests/                  # Automated tests
```
